STILL OUTSTANDING - OPERATIONAL, NOT FIXABLE FROM THE CODEBASE
--------------------------------------------------------------------------------
1. Check every deployed environment for the seeded accounts (admin@example.com,
   test@example.com, demo@example.com) and delete them. If the admin account
   existed on a public host, treat that host as compromised: rotate APP_KEY,
   Stripe keys, database credentials, and invalidate all sessions. (finding 9)

2. Set STRIPE_PAID_ACTION_PRICE_ID in .env.prod. It is empty, so paid actions are
   now refused in production rather than applied for free - the feature is
   disabled until a real price id is set. (finding 2)

2b. STRIPE_WEBHOOK_SECRET is optional for this application and is NOT a security
   requirement - the webhook rejects unsigned events either way. Without it,
   subscription changes made in the Stripe billing portal are only picked up by
   the daily 03:00 subscriptions:sync run, so entitlements can be up to ~24h
   stale. Set it if you want near-real-time billing state. Run
   `php artisan billing:check` on each host to see what is missing; it exits 1 on
   problems and is safe to add to build.sh. (finding 6)

3. Add the web-server rules for /storage: deny execution of .php, and serve
   uploads with Content-Security-Policy "default-src 'none'; sandbox" and
   X-Content-Type-Options: nosniff. The application-side validation is in place,
   but defence in depth here is cheap. (finding 3)

4. Set TRUSTED_PROXIES to the real proxy addresses on each host. It defaults to
   127.0.0.1, which is safe but wrong if a load balancer or Cloudflare sits in
   front - IP-keyed rate limits will otherwise see the proxy's address. (finding 10)

5. Data cleanup for rows written before the fixes: short_links.destination_url and
   qr_codes.content_data entries whose scheme is not http/https, and
   qr_designs.logo_path values that are absolute or contain "..". The render and
   redirect paths already refuse them, so this is hygiene rather than exposure.

6. Decide whether to enforce the CSP (see the note above).

--------------------------------------------------------------------------------
CROSS-CUTTING THEMES
--------------------------------------------------------------------------------
Three patterns account for most of the findings, and are worth fixing as habits
rather than as individual bugs:

1. Authorization is applied inconsistently. QrCodeIndex scopes every lookup to
   `auth()->user()->qrCodes()`, while QrCodeBuilder and TeamManager operate on
   route- or client-bound models with no check at all. A QrCodePolicy already
   exists and is registered - it is simply not called from the builder. Consider
   a convention: every Livewire component that holds a model gets `#[Locked]` on
   that property and an `authorize()` call in both mount() and the write action.
   Note that no `#[Locked]` attribute appears anywhere in the codebase today,
   which means every public property is client-writable.

2. Security controls fail open. Billing without Stripe keys grants the plan
   (7); paid actions without a price id apply for free (2); the Stripe webhook
   without a secret accepts unsigned events (6); quick-login defaults to on in
   the shipped .env template (8). Each of these should throw in production rather
   than degrade silently. A single `assertProductionConfigured()` check at boot
   would cover most of them.

3. Client-supplied data is trusted after the first hop. The base64 `?s=` builder
   state, Livewire public properties, and API request arrays all flow into
   persistence without revalidation - findings 4, 5 and 17. Validate at the
   boundary where data is written, not only where it is first entered.

--------------------------------------------------------------------------------
WHAT WAS CHECKED AND FOUND SOUND
--------------------------------------------------------------------------------
Worth recording so it is not re-reviewed:
* No SQL injection. Every DB::raw() use (AnalyticsService, AggregateAnalytics)
  contains only literal SQL; all user input goes through the query builder.
* No unescaped Blade output in application views - `{!! !!}` appears only in the
  stock vendor mail templates.
* Password storage is correct: bcrypt via the `hashed` cast, 12 rounds,
  `Hash::check()` on the settings path.
* Session fixation is handled - Laravel's SessionGuard migrates the session on
  every login, including the Google and magic-link paths.
* The magic-link route is properly signed and time-limited, and returns an
  identical response whether or not the address exists.
* Secrets are not committed: .gitignore excludes .env and .env.*, and
  `git ls-files` confirms only .env.example is tracked.
* Laravel's /storage/{path} and PUT /storage/{path} routes (local disk, private)
  require valid signed URLs - they are not an upload vector.
* QrCodeIndex, CategoryIndex and AnalyticsApiController scope all queries to the
  authenticated user correctly.
