================================================================================
11 - MEDIUM - Short-link passwords travel in the query string and can be brute
              forced without limit
================================================================================
Status        : FIXED (2026-09-20) - see "FIX APPLIED" at the end of this file
Category      : Sensitive data in URL + missing brute-force protection
                - OWASP A02:2021 / A07:2021
Verified      : Code and template read; route confirmed GET-only
Affected files: app/Http/Controllers/RedirectController.php:63-71
                resources/views/redirect/password.blade.php:21-27
                routes/redirect.php:6-8
                app/Livewire/QrCodes/QrCodeBuilder.php:1009-1011 (password stored)

--------------------------------------------------------------------------------
SUMMARY
--------------------------------------------------------------------------------
Password-protected links prompt with a form that submits by **GET**:

    <form method="GET" action="" class="mt-6">
        <input name="password" type="password" ...>

and the controller reads it from the query string:

    if ($linkData['password_hash']) {
        $password = $request->input('password');
        if (! $password || ! password_verify($password, $linkData['password_hash'])) {
            return response()->view('redirect.password', [...], $password ? 403 : 200);
        }
    }

The route is registered GET-only (`routes/redirect.php`), so the form cannot post.

There is no attempt counter, no delay and no lockout - each guess is an ordinary
page request. The hash is also copied into the shared cache entry for 300 seconds
(`Cache::remember("shortlink:{$slug}", 300, ...)`), so it is read from cache for
most attempts rather than from the database.

Separately, the password is stored with `bcrypt()` but verified with the raw
`password_verify()` rather than `Hash::check()`, so it bypasses the application's
configured hashing driver and rounds.

--------------------------------------------------------------------------------
IMPACT
--------------------------------------------------------------------------------
* The password appears in the URL. That means it is written to web-server access
  logs, proxy and CDN logs, browser history, and the `Referer` header sent to the
  destination site after the redirect - so the owner of the destination learns the
  password protecting the link to it.
* Anyone who can read the victim's browser history or the server's access logs
  recovers every link password used.
* Unlimited guessing: link passwords are typically short and human-chosen (this is
  a "type it off a poster" feature), and there is nothing to slow an attacker
  down. A few thousand requests exhausts most realistic passwords.
* The 403/200 status difference cleanly distinguishes "wrong password" from
  "prompt", which makes scripting the attack trivial.
* This is a paid feature (PaidActionType::ChangePassword), so its failure is also
  a product-integrity problem.

--------------------------------------------------------------------------------
PROPOSED FIX
--------------------------------------------------------------------------------
(1) Accept the password over POST [routes/redirect.php]

        Route::get('/{slug}', [RedirectController::class, 'handle'])
            ->where('slug', '[a-zA-Z0-9_-]+')
            ->name('redirect.handle');

        Route::post('/{slug}', [RedirectController::class, 'unlock'])
            ->where('slug', '[a-zA-Z0-9_-]+')
            ->middleware('throttle:10,1')
            ->name('redirect.unlock');

    and in the view:

        <form method="POST" action="{{ route('redirect.unlock', $slug) }}">
            @csrf
            <input name="password" type="password" ...>
        </form>

(2) Remember the unlock in the session instead of re-sending the password on
    every navigation [app/Http/Controllers/RedirectController.php]

        public function unlock(Request $request, string $slug)
        {
            $request->validate(['password' => 'required|string|max:255']);

            $link = $this->lookup($slug);                 // shared with handle()
            abort_if(! $link, 404);

            $key = 'shortlink-unlock:' . $slug . '|' . $request->ip();

            if (RateLimiter::tooManyAttempts($key, 10)) {
                return response()->view('redirect.password', [
                    'slug'  => $slug,
                    'error' => __('qr.too_many_attempts'),
                ], 429);
            }

            if (! Hash::check($request->input('password'), $link['password_hash'])) {
                RateLimiter::hit($key, 300);

                return response()->view('redirect.password', [
                    'slug'  => $slug,
                    'error' => __('qr.invalid_password'),
                ], 403);
            }

            RateLimiter::clear($key);
            $request->session()->put("shortlink_unlocked.{$slug}", true);

            return redirect()->route('redirect.handle', $slug);
        }

    and in handle():

        if ($linkData['password_hash'] && ! $request->session()->get("shortlink_unlocked.{$slug}")) {
            return response()->view('redirect.password', ['slug' => $slug, 'error' => null], 200);
        }

    Rate limit on slug + IP so one link under attack does not lock out other
    visitors, and use `Hash::check()` so the app's hashing configuration applies.

(3) Keep the hash out of the shared cache. Cache the link metadata without
    `password_hash`, and read the hash from the database only on an unlock
    attempt. It is consulted rarely, and keeping it out of a shared cache store
    (Redis, in this deployment) narrows where it can leak from.

(4) Add `Referrer-Policy: no-referrer` on the redirect responses so the previous
    URL is never forwarded to the destination site.

================================================================================
FIX APPLIED (2026-09-20)
================================================================================
The password is now submitted to a POST /{slug} unlock route with CSRF, verified
with Hash::check(), rate limited at 10 attempts per 5 minutes keyed on slug+IP,
and the result remembered in the session so it is not re-sent on every
navigation. The password_hash is no longer copied into the shared cache entry -
only a boolean is - and is read from the database on an unlock attempt.
Referrer-Policy: no-referrer is set on the prompt and on the redirect.

Files: app/Http/Controllers/RedirectController.php, routes/redirect.php
       resources/views/redirect/password.blade.php
Tests: tests/Feature/RedirectControllerTest.php (4 new cases, including that a
       password in the query string no longer unlocks anything)

Full suite after the change: 130 passed (367 assertions).
